# payment-worker Agent Notes

This Worker owns the Telegram payment bot.

- `/pay` records tenant payments through the wizard and writes Payment records to Airtable. It lists active tenancies plus ended ones that still owe money.
- `/movein` (`src/movein.ts`, prompts in `src/movein-view.ts`) creates a Tenant (unless one is reused), a Tenancy, the first rent Charges, sets the Room to Occupied, then creates the Bond charge when there is one. It writes in that order with no rollback. The Bond charge (`buildBondCharge` in `@rent/tenancy`) must not get a `Period`: the charge generator treats any charge with next month's `Period` as that month's rent.
- `/moveout` (`src/moveout.ts`) sets the tenancy `End Date`. It sets the Room to Vacant only when the end date is today (Melbourne) or earlier.
- Callback data prefixes: `mi:` for move-in, `mo:` for move-out. `/pay` keeps its own unprefixed callbacks.
- Every confirm screen gets an operation ID from `newOpId()` (`src/confirm.ts`). Store it in the session as `opId` and put it in the Confirm button with `confirmData(prefix, opId)`. Match the button with `confirmPattern(prefix)`, and refuse it when its ID doesn't match the session's.
- Before any Airtable write, a Confirm must call `claimSave(ctx, env, opId, flow, savingText)` and stop unless it returns true. It asks `claimConfirm()`. That call goes to the `ConfirmLock` Durable Object, which gives each operation ID to one tap only. The KV `saving` step comes after the claim; it is not the guard, because KV `get`/`put` can't stop two taps that arrive together. Keep both. `claimSave` also decides the reply: when another tap has the save, it edits the screen to `savingText`; when the lock can't be reached, it leaves the confirm screen and its buttons alone and sends the error as a new message, so the same Confirm can be tapped again. A new confirm flow needs all of this too.
- Every button and typed-text handler checks the session's `flow` and `step` before it reads Airtable or changes the session, and replies "expired" when they don't match. Use `sessionAt` (`/movein`), `paySessionAt` (`/pay`), or the same check inline (`/moveout`). Only the first list of a flow may start a new session: `/pay`'s tenant list (`tenancy:`) and `/movein`'s room list (`mi:r:`). This is what keeps a button from an earlier screen, which stays visible in the chat, from moving a session out of `saving` and opening a second save. A Cancel clears only its own flow's session.
- `test/integration/saving-session.test.ts` taps every button and types text against a `saving` session of each flow, and checks that the session, Airtable and the shown buttons don't change. Add each new button's callback data to its `BUTTONS` list.
- `/movein` stores the charges its confirm screen showed (`plannedCharges`). Confirm works them out again and shows the screen again if they changed, before claiming.
- Build the Airtable client with `airtableFor(env)` (`src/airtable.ts`, 4 s per request). grammY gets a 50 s webhook timeout (`WEBHOOK_TIMEOUT_MS` in `src/budget.ts`) so a Confirm's writes can all finish. `MOVE_IN_CONFIRM_WORST_CASE_MS` in the same file adds up the move-in Confirm's writes, and `test/timeouts.test.ts` fails if they don't fit. When you add an Airtable call to a Confirm, add it there too.
- Replies and logs must never include raw Airtable response bodies. Replies show only the HTTP status (`httpStatusOf`) and link to the record. Logs go through `logAirtableFailure(flow, action, error)`, which writes the action and the status only. A 5xx, timeout or unreadable response may have saved, so the reply says to check before retrying.
- Due-date, charge and tenancy rules live in `packages/tenancy`. Do not copy them into this Worker.
- `/reminder` is read-only and shows overdue plus next-14-day outstanding charges.
- Keep Airtable access through `@rent/airtable-client`; do not add one-off fetch helpers.
- Keep linked-record filtering client-side when matching Charges to Tenancies.
- `/reminder` must remain charge-level: a tenant can have multiple overdue months and can appear in both reminder sections.
- `/reminder` output should stay sorted by due date: tenant groups use their earliest due date, and rows within a tenant are due-date ordered.
- Update `payment-worker/README.md`, root `README.md`, `docs/runbook.md`, root `AGENTS.md`, and `CLAUDE.md` when bot commands or operational behavior change.
